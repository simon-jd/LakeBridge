# 切换、消费者回退与合法数据处理

## 发布切换清单

- H0 与 H1 均是 manifest 到达批次边界，已校验源文件，原始接入继续产生后续批次。
- 实际停用旧写入任务，等待在途作业结束；外部写者不得绕过本项目控制层。
- 取得数据集持久锁，确认上一运行无未处理提交；记录排队时长和发布代次。
- 主键、精确单位、套餐关系、汇总、范围外校验全部通过，差异可追查。
- 发布快照已建立保护 tag；先持久化 candidate，再推进单表 main，最后原子切 active_release。
- 消费者只解析一次 release，使用其全部 snapshot_id；用 `query --release ...` 核验样例。
- 后续批次到达并通过查询验证后，保留旧路径/配置至回退窗口结束，再单独退役旧任务。

本项目不模拟一个并不存在的旧生产调度器；“停用旧写者”在真实接入中是必须实际执行的外部步骤。

## 错误发布回退

`rollback <release_id> --reason ...` 先检查所有快照可读，再用 generation CAS 切消费者指针。
不能在写入运行持有所有权期间执行切换。原 main、源进度和合法新增保持不变。
旧发布的数据天然不包含后来的新增，因此消费者回退是恢复可信历史的临时措施，不等于数据永久修复。

随后用最新 HWM + 正确规则进行前向修正，发布一个同时包含历史修复和合法新增的新 release。
demo 会在错误规则发布后接入 batch 3，消费者切回 batch 2，再以 HWM 3/v1 修正，确认新增仍保留。

## 写入表回退

本项目只在独立 compatibility 表中验证底层 rollback_to_snapshot。没有提供随意回滚业务 main 的
快捷命令，因为它可能删除错误之后的合法提交。若必须做底层回退，先停写、枚举后续合法提交，
准备回滚后重放方案与校验，再操作。catalog 元数据与仍被引用的数据文件都必须存在；快照不是备份。
