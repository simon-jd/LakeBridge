# 10 GiB 本机多 Worker 实测与云费用情景

2026-09-06，实验 `sim_10g_20260906` 已通过。真实压缩源数据 **10.157 GiB、19,773,338 行**，
在本机三个 Spark Worker 上完成旧 Parquet 读取、两种 Iceberg 布局写入、全量对账和文件合并。
完整实验耗时 **587.108 秒（9 分 47 秒）**，包含生成、校验、全部重复查询与进程启动/停止。
没有部署 AWS 资源，也没有产生本实验的云账单；以下费用是有明确假设的情景小计。

运行方法、限制和全部费率来源见 [复现说明](local-simulation.md)，
原始证据见 [report.json](../benchmarks/results/local-10g/report.json)，
文件完整性见 [SHA-256 清单](../benchmarks/results/local-10g/sha256.json)。

## 数据与正确性

源数据大小为 10,906,497,067 字节，720 个 Zstandard Parquet 文件，30 个日期目录。
每行 ID 唯一，附带由 ID 独立派生的 1024 字符 trace 宽列，生成器设定约 60% 热点租户。
这次量测是合成宽事件的存储与性能专项；SaaS 套餐关联、迟到修订、发布和恢复闭环
仍使用此前的小样本业务验收，不能把本结果写成已完成 10 GiB SaaS 全流程迁移。

两张迁移表及合并前后均通过全列双向 `EXCEPT ALL`。另外校验 19,773,338 行、
ID 范围 0–19,773,337、精确 units 合计 9,888,492,088.339000 和全语义列指纹。
所有查询重复的结果相等，可比较变体之间结果也相等。

| 阶段 | 实测秒数 |
|---|---:|
| 校准压缩率 / 正式源数据生成 | 3.745 / 52.654 |
| 无分区 Iceberg 写入 / 全量对账 | 38.212 / 99.190 |
| 日期分区 Iceberg 写入 / 全量对账 | 40.365 / 103.970 |
| 文件合并 / 合并后全量对账 | 34.970 / 116.922 |

## 性能结果

每个查询预热 1 次、量测 3 次，固定执行顺序并清 Spark cache；JVM/OS/对象存储缓存未清空。
日期查询只读取所需的时间与用量列；全扫描查询会读取整个 trace_payload 并计算校验聚合。

| 查询 | 三次实测秒数 | 中位秒数 | 每次实际 S3 读请求 |
|---|---|---:|---:|
| 旧日期目录 Parquet，单日查询 | 0.175177 / 0.096633 / 0.096750 | 0.096750 | 72 GET + 96 HEAD |
| 无分区 Iceberg，单日查询 | 0.684361 / 0.941303 / 0.544208 | 0.684361 | 457 GET |
| 日期分区 Iceberg，单日查询 | 0.097645 / 0.088855 / 0.085146 | 0.088855 | 73 GET |
| 合并前，全量宽列查询 | 9.747179 / 9.715483 / 9.649296 | 9.715483 | 2,161 GET |
| 合并后，同一全量查询 | 9.273940 / 8.358294 / 8.407307 | 8.407307 | 271 GET |

在这次样本中，日期分区相对无分区表将中位耗时降低 **87.0%**，匹配文件从 96 个变为 24 个，
匹配文件字节从 10,887,858,057 降为 363,172,329。它们是匹配文件总大小，不是实际网络读取量。
旧 Parquet 已有有效日期目录裁剪，0.097 秒与分区 Iceberg 的 0.089 秒接近，
不能将这组数据解释为单纯转换格式即可获得 87% 提速。

| 日期分区表 | 合并前 | 合并后 |
|---|---:|---:|
| 当前文件数 | 720 | 90 |
| 当前 Parquet 总字节 | 10,888,619,040 | 10,885,578,390 |
| 文件中位大小 | 14.42 MiB | 115.34 MiB |
| 全量查询中位耗时 | 9.715 秒 | 8.407 秒 |

合并减少 **87.5%** 的文件、改善 **13.5%** 的查询时间，但当前文件总字节只下降约 **0.028%**。
合并自身花费 34.970 秒，加精确对账共 151.892 秒。目标文件大小 128 MiB，实际中位约 115 MiB。
`before_compaction` tag 仍在，旧文件继续占空间。本次结果说明文件合并主要减少请求与调度，
没有取得显著的压缩容量收益。样本仅三次，不能据此承诺稳定的生产提速比例。

## 资源和物理存储

实际 Spark application 为 `app-20260906233939-0003`，event log 记录 worker1/2/3
各一个 4-core executor。整个实验有 **3,812 个 task attempts，失败 0**。
shuffle 写入、读取各 258.394 GiB；task input bytes 累计 273.433 GiB，均包含全量对账与重复查询。
`Disk Bytes Spilled` 为 0，仍有正常 shuffle 临时文件和大量磁盘 I/O。

Docker 每 2 秒采样，共 291 组，采样错误 0。全服务同时 working set 的观测峰值为
**26.788 GiB**，包含文件缓存的 cgroup memory 峰值为 **55.175 GiB**；容器限制合计 68 GiB。
部分 Worker 的文件缓存已接近各自 16 GiB 上限，内核回收缓存可能影响 I/O。
累计观测 CPU 用量约 6,094.385 core-seconds，首尾少量时间可能漏采；不作为云计费时长。

S3 代理记录 81,593 个完成请求，其中 42,586 GET、27,295 HEAD、4,644 LIST、3,732 PUT、
362 POST、2,974 DELETE；服务端 5xx 为 0，3,809 个 404 是文件/目录存在性探测。
各阶段计数与跨阶段总计略有区别，原始 [请求汇总](../benchmarks/results/local-10g/s3-summary.json)
和 [任务/资源证据](../benchmarks/results/local-10g/event-summary.json) 均已保留。

按对象清单，本次正式实验保留 **1,651 个对象、40.638 GiB**，包含源、pilot、两个 Iceberg 表、
旧 tag 数据和元数据；不含其他冒烟试跑及本地 shuffle。按 $0.023/GiB 月假设，
这些完整实验对象若保留一个月约 $0.935。没有删除旧文件或将引用过期的假设计成已实现收益。

## 云费用情景

[费率文件](../benchmarks/cloud-cost-assumptions.json) 采用 4 台 m6i.xlarge 的
$0.192/台时参考值，以及明示的 S3 / gp3 价格；来源及复核日期均列在文件中。
四块 100 GiB gp3 保留整月，每月合计 $32。云端运行时长分别假设为本机的 0.5/1/2 倍。
这些倍数未在真实云实例校准，不能当成预测区间。

月度情景固定为 30 天、每天 100 次全量宽列查询、一次批次和预热、600 秒启动预算。
首月共同计入一次分区表加载与精确对账；优化方案再计一次合并及对账，旧快照保留整月。
源数据保留，未加入持续增长或迟到修订。两个场景都保留完整四块 EBS 卷。

| 云端耗时 / 本机耗时 | 合并前月度小计 | 合并后月度小计 | 情景差额 |
|---|---:|---:|---:|
| 0.5 倍 | $42.09 | $39.64 | $2.45，5.83% |
| 1 倍 | $45.24 | $42.39 | $2.85，6.30% |
| 2 倍 | $51.55 | $47.90 | $3.65，7.09% |

1 倍情景的合并后小计由计算 $9.346、EBS $32、S3 数据文件保留 $0.700、观测请求 $0.346 组成。
因旧文件保留，S3 数据文件存储反而从 $0.467 增加到 $0.700；请求和计算的下降抵消了它。
若四台实例整月常开，仅计算资源就为 $552.96，同口径总小计约 $588.06 → $586.01。
查询提速不自动缩短实例开机时间，不能把 13.5% 查询改善直接套到整张账单。

本次完整实验的“计算 + 观测阶段请求”小计在 1 倍情景为 $0.325，
其中另加了 600 秒云端启动预算；它尚未包含 EBS 和对象保留，不能称为完整云端实验报价。
所有情景均排除了元数据小对象、监控、备份、NAT/跨 AZ/公网费用、Airflow、托管 RDS/EMR、
税费及本机电费折旧。完整明细在 [cost-estimate.json](../benchmarks/results/local-10g/cost-estimate.json)。

## 验证与试跑问题

新增的计价与请求日志测试，以及原有业务/Spark 集成测试，共 **49 passed（35.18 秒）**，
见 [回归日志](evidence/simulation-regression.log)。完整正式运行没有失败 task、观测错误或 S3 5xx。

准备阶段先发现 MinIO 监控指标缓存会漏掉短查询计数，改用逐请求代理日志。
代理首轮试跑因未复用上游连接出现端口耗尽和 502，已通过上游 keepalive 修复；
修复后独立试跑成功，再启动正式实验。带 502 的试跑未纳入上述性能和费用结论。
